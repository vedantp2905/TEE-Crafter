# `fintech_fraud_detection` — confidential transaction risk scoring

A minimal **stdin → stdout** Python app that scores credit-card-style
transactions against a deterministic fraud rule engine. Demonstrates the
classic "score sensitive financial events without exposing them to the
cloud operator" use case.

## What it does

- **Input** (`input/data.json`): list of transactions with `txn_id`, `user_id`,
  `amount`, `currency`, `timestamp`, `merchant_category`, geo `location`,
  `device_id`.
- **Output**: `{"env_injection": {…}, "results": [{"txn_id", "risk_score",
  "is_blocked", "triggered_rules"}, …]}` (shape defined by your app; the
  framework does not enforce a JSON schema). The `env_injection` block proves
  `--secrets-env` delivery: `score_threshold` is read from the injected `.env`
  and actually drives the block decision, while `database_url_loaded` /
  `risk_api_token_loaded` confirm the sealed secrets arrived (without leaking
  them). `env_injection_ok` is `false` if the `.env` never arrived.
- **Scoring**: pure-Python rule chain in `core/`; no network egress from
  inside the TEE.

## Run it locally first (no TEE)

```bash
cd examples/fintech_fraud_detection
pip install -r requirements.txt
cat input/data.json | python app.py
```

## Deploy confidentially

```bash
# 1) Bake a hardened image once per platform (re-use across deploys).
tee-crafter internal bake-ami --tee-platform snp-aws
# prints AMI / Azure image / GCP image URI -> use as <IMAGE_ID> below

# 2) Deploy + run the client + tear down.
#    You must pass exactly one of --batch or --persistent; there is no default
#    (apps/cli/src/tee_crafter/cli/commands/deploy/deploy_helpers.py::validate_run_mode).
tee-crafter deploy \
  --source ./examples/fintech_fraud_detection \
  --tee-platform snp-aws \
  --ami-id <IMAGE_ID> \
  --persistent \
  --deploy --auto-approve --teardown
```

> The deploy-time client verifies the TEE attestation and exits — that is its
> only job. Your own client sends real requests to the container's API over the
> same attested channel; the framework neither defines nor inspects that data.

Swap `--tee-platform` to any of the ten supported platforms — `nitro-aws`,
`snp-aws`, `snp-azure`, `snp-gcp`, `tdx-azure`, `tdx-gcp`, `sgx-azure`,
`gpu-cc-aws`, `gpu-cc-azure`, `gpu-cc-gcp` — and the same source ships
unchanged. `sgx-azure` is batch-only, so pair it with `--batch`.

### Persistent service mode + SIEM (real-time fraud scoring API)

```bash
tee-crafter deploy \
  --source ./examples/fintech_fraud_detection \
  --tee-platform snp-aws \
  --ami-id <IMAGE_ID> \
  --persistent --service-profile long-lived \
  --siem syslog-cef --siem-config ./apps/cli/siem-sandbox/configs/syslog-via-ngrok.json \
  --byok aws-kms     --byok-config ./apps/cli/byok-sandbox/configs/byok-snp-aws.json \
  --deploy --auto-approve
```

> `syslog-via-ngrok.json` is **generated**, not checked in — create it with `python apps/cli/siem-sandbox/scripts/make_remote_syslog_siem_config.py` (see [docs/siem.md](../../docs/siem.md)).

Drops the one-shot client + `--teardown`, leaves a 24 h / 1 h re-attest
RA-TLS service running, streams continuous-attestation events to the
syslog/CEF SIEM, and binds the customer KMS key release to the SNP measurement
— **advisorily** on `snp-aws`, where AWS KMS has no SEV-SNP condition key, so
the real gate is IAM. See [byok.md](../../docs/byok.md#per-provider-gating).

The `configs/*.json` paths are generated by the sandbox helpers in
`apps/cli/{siem,byok}-sandbox/`, not checked in — run those first. On GCP use
`--byok gcp-kms --byok-config ./apps/cli/byok-sandbox/configs/byok-gcp.json`.

### Secrets + database egress (`.env`)

This example ships a [`.env`](./.env) with a `DATABASE_URL` and `RISK_API_TOKEN`.
Because those are real secrets, seal them with BYOK and open a default-deny
allowlisted egress path to the database:

```bash
tee-crafter deploy \
  --source ./examples/fintech_fraud_detection \
  --tee-platform snp-aws \
  --ami-id <IMAGE_ID> \
  --persistent --service-profile long-lived \
  --secrets-env ./examples/fintech_fraud_detection/.env \
  --byok aws-kms --byok-config ./apps/cli/byok-sandbox/configs/byok-snp-aws.json \
  --egress-mode nat --egress-allow db.internal:5432 \
  --deploy --auto-approve
```

- `--secrets-env` + `--byok` envelope-seals the `.env`; the cleartext is
  released **only inside the attested enclave** (tmpfs `/run/tee_crafter/app.env`)
  and surfaces to the app as `os.environ["DATABASE_URL"]` etc.
- `--egress-mode nat --egress-allow db.internal:5432` keeps egress
  **deny-by-default** and opens just the database CIDR (via NAT for public
  endpoints). Drop `--byok` and the `.env` is instead baked into the measured
  image — fine for config, not for the secrets above.

## Batch mode

This example is a plain **stdin → stdout** app (`app.py`). Batch mode runs the Dockerfile to completion:

```bash
tee-crafter deploy \
  --source ./examples/fintech_fraud_detection \
  --tee-platform snp-aws \
  --ami-id <IMAGE_ID> \
  --batch \
  --input-dir ./examples/fintech_fraud_detection/input \
  --deploy --auto-approve --teardown
```

> Batch mode mounts `--input-dir` read-only at `/input` inside the container;
> the Dockerfile reads `/input/data.json`. Put your input file(s) in that
> directory. The sample `input/data.json` shipped here exercises all three
> verdict paths (clean, scored-but-under-threshold, blocked).
>
> `--input-dir` is uploaded as a plain `tar.gz` and extracted **in the clear on
> the host**, so it is not a confidentiality control — see
> [the caveat in the examples README](../README.md#what---input-dir-actually-does--read-this-before-sending-real-data).
> The container writes to `/output`, which the Dockerfile creates: batch capture
> works by `docker diff`, so anything the container writes into its own layer is
> collected into `output.tar.gz`.

## Latest CLI surface

The deploy command above uses the canonical flag set; see
[`docs/cli_reference.md`](../../docs/cli_reference.md) for the full
matrix. Highlights specific to this example:

| Flag                | Why it matters here                                                  |
|---------------------|----------------------------------------------------------------------|
| `--tee-platform`    | `snp-aws` chosen above for AMD SEV-SNP memory encryption (Milan/Genoa). Any of the 10 TEE backends works. |
| `--instance-type`   | Shape to deploy (vCPU/RAM from it); omit for the platform default. `--spot` for preemptible. `tee-crafter list-instances` to discover. |
| `--ami-id`          | Mandatory with `--deploy` (or set `TEE_CRAFTER_AMI_ID` in `.env`).   |
| `--input-dir`       | Batch only: local dir uploaded as a plain `tar.gz` and mounted read-only at `/input` (Dockerfile reads `/input/data.json`). Not encrypted to the TEE. |
| `--service-profile` | `long-lived` for an attested fraud-scoring API. `default` is one-shot, but under `--persistent` it is silently promoted to `long-lived` (`validate_run_mode`), so pass the profile you actually want. |
| `--batch` | One-shot job via Dockerfile; outputs captured in `output.tar.gz`. |
| `--siem`            | Off-TEE-side audit trail of every attestation event.                 |
| `--byok`            | KMS-backed CMK that only releases on a valid SNP measurement.        |
| `--allow-vulnerable`| Override the CRITICAL/HIGH Trivy gate (recorded in provenance).      |
