# Intel SGX via Gramine on Azure — Detailed Flow

## What is Intel SGX?

**Intel Software Guard Extensions (SGX)** is a set of CPU instructions that allow user-level code to allocate private regions of memory called **enclaves**. Code and data inside an enclave are protected from all software outside it — including the operating system, hypervisor, and firmware. Only the CPU itself can access enclave memory.

SGX enclaves are measured at load time: the CPU computes a cryptographic hash of the enclave's initial code and data, producing an **MRENCLAVE** measurement. The signing key used to authorize the enclave is hashed into **MRSIGNER**. Remote parties verify these measurements through **DCAP (Data Center Attestation Primitives)** — Intel's protocol for generating and verifying attestation quotes.

**Gramine** is a library OS (LibOS) that allows unmodified Linux applications (like Python scripts) to run inside SGX enclaves without rewriting them. Gramine intercepts system calls and emulates a Linux environment within the enclave boundary.

### Key Concepts

| Concept | Description |
|---------|-------------|
| **MRENCLAVE** | Hash of the enclave's code and data at load time — uniquely identifies the enclave binary |
| **MRSIGNER** | Hash of the RSA-3072 signing key — identifies who signed the enclave |
| **DCAP** | Data Center Attestation Primitives — Intel's quoting/verification protocol for SGX |
| **RA-TLS** | Remote Attestation TLS — embeds a DCAP quote inside an X.509 certificate extension |
| **AESM** | Application Enclave Services Manager — Intel's service that manages quoting enclaves |
| **QPL** | Quote Provider Library — fetches provisioning certificates (Azure provides `az-dcap-client`) |
| **EPC** | Enclave Page Cache — protected memory region where enclave code/data resides |
| **Gramine** | Library OS that runs unmodified Linux apps inside SGX enclaves |
| **SIGSTRUCT** | Signed enclave metadata generated by `gramine-sgx-sign` — contains MRENCLAVE |

## Architecture

```
┌──────────────────┐ ┌───────────────────────────────────────────────────┐
│ │ SSH port-forward │ Azure DCsv3 VM (SGX-capable, no public IP) │
│ Local Client │ via Bastion tunnel │ │
│ (client_sgx.py) │ (localhost:PORT → VM:5005) │ ┌──────────────────────────────────────────────┐ │
│ │ ─────────────────────────────► │ │ Gramine-SGX Enclave (EPC memory) │ │
│ 1. TLS connect │ │ │ │ │
│ 2. Extract quote│ RA-TLS │ │ app_gramine.template.py (rendered) │ │
│ 3. Verify DCAP │ │ │ ┌────────────────────────────────────────┐ │ │
│ 4. ECIES encrypt│ │ │ │ ECDH P-256 keypair (in-enclave) │ │ │
│ 5. Send data │ │ │ │ RA-TLS certificate (quote in X.509 ext)│ │ │
│ 6. Get result │ │ │ │ TLS server on 127.0.0.1:5005 │ │ │
│ │ │ │ │ ECIES decrypt (AES-256-GCM) │ │ │
└──────────────────┘ │ │ │ forward → graminized container │ │ │
 │ │ └────────────────────────────────────────┘ │ │
 ┌───────────────┐ │ └──────────────────────────────────────────────┘ │
 │ Azure Bastion │ │ │
 │ (Standard SKU) │ SSH tunnel │ SGX AESM Service (DCAP quoting) │
 │ tunneling_on │ ─────────────────────────►│ az-dcap-client QPL (Azure cert caching) │
 └───────────────┘ └───────────────────────────────────────────────────┘
```

### Data Flow

```
Client SGX Enclave (Gramine)
 │ │
 │── TLS connect (verify_mode=CERT_NONE) ──────────► │
 │ │ (RA-TLS cert presented)
 │◄── Server certificate (DER) ──────────────────────│
 │ │
 │ Extract DCAP quote from X.509 extension │
 │ (OID 1.2.840.113741.1.13.1) │
 │ │
 │ parse_sgx_quote: │
 │ MRENCLAVE at report_body[64:96] │
 │ MRSIGNER at report_body[128:160] │
 │ REPORT_DATA at report_body[320:384] │
 │ │
 │ verify_dcap_quote_signature: │
 │ ECDSA-P256 over quote header+body │
 │ │
 │ verify_qe_report_binding: │
 │ QE report_data[:32] == SHA256(att_key||auth) │
 │ │
 │ verify_pck_cert_chain: │
 │ PCK → Intermediate → Intel SGX Root CA │
 │ │
 │── {get_attestation, nonce} ──────────────────────►│
 │ │ Generate DCAP quote with
 │ │ SHA256(ECDH_PUB) in report_data
 │◄── {enclave_public_key, attestation_doc} ─────────│
 │ │
 │ Verify: report_data[:32] == SHA256(pub_key) │
 │ │
 │ ── attestation verified; client prints │
 │ {"status":"attestation_verified"} and exits ──│
```

> The deploy-time client's only job is to **verify attestation** and exit. It
> sends no application data. In production your own client opens the same kind
> of attested tunnel and sends real, app-specific requests to your container's
> API — the framework never defines or inspects "the data".

## SGX deployment model (batch-only)

Intel SGX on Azure (`sgx-azure`) supports **`--batch` only** in the current
release. User Docker images are graminized via **Gramine Shielded Containers
(GSC)** when the `gsc` CLI is available; `MRENCLAVE`/`MRSIGNER` are derived
from the signed graminized image. **`--persistent` is rejected** at CLI parse
time — use a VM-class TEE for long-lived services.

```bash
tee-crafter deploy --source./examples/fintech_fraud_detection \
 --tee-platform sgx-azure --batch \
 --input-dir./examples/fintech_fraud_detection/input \
 --deploy --auto-approve --teardown
```

### Batch pipeline (GSC)

| Step | Action | Details |
|------|--------|---------|
| 1 | **Docker build** | Build user image from `Dockerfile` |
| 2 | **GSC graminize** | `gsc build` + `gsc sign-image` on the SGX host (when available) |
| 3 | **Batch run** | Container runs to completion; batch collector packages outputs |
| 4 | **Attestation** | Deploy-time DCAP quote + signed audit bundle (no live RA-TLS client) |

See [execution_model.md](execution_model.md) and `cli/deployment/sgx/gsc.py`.

#### Two things the enclave needs from outside itself

Neither is visible from the code, and each presents as a problem with a
different layer than the one at fault — so both are recorded with the evidence
that identified them.

**AppArmor has to allow `open("/")` explicitly.** The batch profile ends with
`/** rwlkmix,` and reads as "allow everything" — but in AppArmor `/**` matches
paths with at least one character after the slash and does **not** match the
root directory. Gramine's loader opens `/` while building its own filesystem
view, so every batch run died before `libos_init` finished:

```
[P1:T1:] error: Mounting "file:/" (chroot) under / failed: Permission denied (EACCES)
[P1:T1:] error: libos_init failed in init_mount_root: Permission denied (EACCES)
```

That names a Gramine mount and reads like a manifest problem. The kernel named
the real culprit:

```
apparmor="DENIED" operation="open" profile="tee-crafter-batch-container" \
 name="/" comm="loader" requested_mask="r"
```

Isolated by running the graminized image four ways — full profile, no AppArmor,
no seccomp, neither. Only the AppArmor-free variants got past it; seccomp was
innocent. `/ rwlkmix,` fixes it. Note the *strict* profile
(`apparmor-container`, used by service mode) has carried `/ r,` all along, so
this was drift between two profiles rather than a gap in both — which is why
only batch mode was affected.

**The batch I/O paths have to be declared, and GSC cannot do it.** Gramine
denies any host file it was not told about, by design, so an undeclared `/input`
gives `cannot open /input/data.json: Permission denied` and an undeclared
`/output` gives `cannot create /output/results.json: Permission denied`.
`/input` is a docker bind mount the batch unit adds at run time
(`-v /var/lib/tee_crafter/input:/input:ro`), so it is not in the image and GSC
cannot infer it.

It also cannot be declared in the manifest fragment handed to `gsc build`.
GSC's `finalize_manifest.py` reads `sgx.trusted_files`, `sgx.allowed_files` and
`sgx.protected_files` out of that fragment and pushes all three through the same
expansion, which requires every path to exist in the image at build time and
then records a sha256 for it *in `trusted_files`*. A run-time bind mount can
never satisfy the first condition — the build dies with GSC's own
`NameError: name 'ManifestError' is not defined`, which hides the path it was
complaining about — and if it did, the path would come back *measured*, so a
per-run input could never match its recorded hash.

The declaration therefore goes in **between `gsc build` and `gsc sign-image`**.
That seam works because `gsc sign-image` only runs `gramine-sgx-sign` over
whatever manifest it finds; it does not re-run the finalizer. So GSC keeps its
measured `trusted_files` for all of the application's own code, and MRENCLAVE
still covers the insertion, because the signature is computed over the patched
manifest — the allowance is attested rather than smuggled in.
(`deployment/sgx/gsc.manifest_patch_dockerfile`.)

The cost is real and is surfaced rather than hidden. Gramine prints this on
every run:

```
Gramine detected the following insecure configurations:
 - sgx.allowed_files = [... ] (some files are passed through from
 untrusted host without verification)
Gramine will continue application execution, but this configuration
must not be used in production!
```

The enclave does not verify `/input` or `/output`. Input integrity rests on the
input digest recorded in the signed audit trail, and `/output` is host-visible
in the clear, which is inherent to capturing output with `docker diff`. The
alternative — measuring the input, whose hash is known at deploy time — is
stronger but makes MRENCLAVE change with every input, so a pin could no longer
be compared across runs. `sgx.file_check_policy = "allow_all_but_log"` is not an
option at all: under that setting GSC skips trusted-file generation entirely,
which would leave the application's own code unmeasured.

### Base-image support, and one patch we apply to GSC

Any Debian- or Ubuntu-derived base works, including `python:3.12-slim`. That is
worth stating explicitly because it is not true of stock GSC, and getting there
means TEE-Crafter patches GSC's own Dockerfile templates at install time —
a third-party build system modification, so it is documented rather than
buried.

GSC is pinned at commit `0b2ba93`, and its
`templates/debian/Dockerfile.compile.template` (which the Ubuntu template
extends verbatim, so this is the shared path) registers Intel's SGX apt
repository with `apt-key`. Two things break on Debian 13 "trixie", which is what
`python:3.12-slim` reports:

1. `apt-key` was removed in Debian 13, so the Gramine compile stage dies with
 `apt-key: not found`, exit 127.
2. Fixing only that is not enough. Debian 13 ships apt 3.0.3, which verifies
 signatures with `sqv` (Sequoia) rather than `gpgv`, and Sequoia rejects
 Intel's signature: *"Malformed MPI: leading bit is not set"*, and then
 *"The repository... is not signed"*. The signature is not actually bad —
 `gpgv` on the same `InRelease` and key reports `Good signature from
 "CN=Intel(R) Software Development Products"`. Sequoia is simply stricter
 about MPI encoding than the GnuPG that produced it.

`scripts/sgx_azure/patch_gsc_debian_template.py` rewrites that block to install
`gpgv`, drop Intel's (already ASCII-armored) key into
`/etc/apt/keyrings/intel-sgx.asc`, reference it with `signed-by=`, and point apt
at `gpgv` for verification. **Signature verification stays on** — the patch
changes *which* verifier runs, not *whether* one runs. `[trusted=yes]` was
rejected outright: it would install Intel's SGX libraries unverified in a
project whose purpose is verifiable execution.

Two properties worth knowing:

- The `APT::Key::gpgvcommand` override is written in GSC's **compile** stage,
 which exists only to build Gramine. GSC's build stage copies `/gramine/` out
 of it and discards the rest, so the override never reaches the graminized
 image that gets measured.
- The patch is idempotent and fails loudly. If a future GSC pin reformats that
 block, the patch exits non-zero at bake time instead of half-applying, and
 both install sites (`apps/cli/Dockerfile` and `scripts/sgx_azure/setup_sgx.sh`)
 assert the post-condition by grepping for `signed-by=`.

There is no upstream fix to wait for: GSC `master` still calls `apt-key`, and
the pinned commit *is* master's tip.

### Graminizing needs internet egress, and this platform denies it

Worth stating before the patch above reads as the whole story, because it is
not. Graminizing is a **source build**: GSC's compile stage is `FROM debian:13`,
installs build tooling from `deb.debian.org`, adds Intel's SGX repository from
`download.01.org`, and clones Gramine from GitHub. Every one of those is
ordinary internet egress.

`sgx-azure`'s NSG denies it. The only outbound rules
`templates/sgx/main.template.tf` writes are the Azure platform IP, IMDS, and
HTTPS scoped to `VirtualNetwork` — then `DenyAllOutbound`. So `gsc build` died
at `Step 1/30: FROM debian:13` with a Docker Hub `i/o timeout`, about
twenty-five minutes into a deploy, after Terraform, Bastion and a 50 MB image
upload had already been paid for.

Measured on the VM: `curl https://registry-1.docker.io/v2/`
returned nothing at all, and adding a single temporary Outbound rule for 80/443
made the identical `gsc build` run to completion in about eight minutes,
producing the first MRENCLAVE this project has ever measured (see below).

Two consequences:

- `batch._check_graminize_egress` probes the VM's egress **before** starting the
 build and fails in seconds with that diagnosis, rather than at minute
 twenty-five with a Docker error.
- The fix is **bake-time**, because this platform is pre-baked-only:
 `sgx-azure --batch` never runs `setup_sgx.sh` at deploy (that call sits on the
 unreachable `--persistent` path), so whatever the VM needs has to be in the
 image already. The trap to avoid is writing GSC's `config.yaml` with
 `Repository` + `Branch`, which is precisely the instruction *"compile Gramine
 from source, later, on the deploy VM"* — the compile then happens where there
 is no egress.

 `setup_sgx.sh` §5c therefore runs **`gsc build-gramine`** during the bake,
 where egress exists, and rewrites `config.yaml` to set `Gramine.Image`, also
 pre-pulling `debian:13` alongside the app base images. GSC skips
 the compile stage outright when that is set
 (`templates/Dockerfile.common.build.template` lines 1-6), so deploy-time
 graminizing no longer pulls `debian:13`, no longer touches Intel's repository
 or GitHub, and no longer spends ~8 minutes compiling. It also moves the
 Debian-13 `apt-key` patch to bake time, where it belongs.

 `Distro` is pinned to `debian:13` for that pre-build (GSC refuses `auto` for
 `build-gramine`) while the deploy-time config keeps `Distro: "auto"` — only
 the Gramine binaries are pinned; GSC still detects the *app* image's distro
 for its build stage. An app image from a different distro family may hit a
 glibc mismatch against those binaries; that is the documented cost of
 pre-building.

### The one thing that cannot be pre-baked

GSC's **build** stage is `FROM <the user's image>` and `apt-get install`s
Gramine's runtime dependencies (`binutils`, `python3-protobuf`, `python3-tomli`,
…) into it. The user's image is not known until deploy, so this single apt
transaction is the entire remaining egress requirement.

It gets the smallest hole that works, and only for as long as it is needed:

| | |
|---|---|
| **Path** | the NAT gateway, provisioned via `local.needs_nat`. An NSG `Allow` with no NAT permits traffic that has nowhere to go — these VMs have no public IP and Azure withdrew default outbound access |
| **Policy** | `AllowGraminizeEgress`, priority 125, TCP 80/443 to `Internet`, created only when `var.graminize_egress` is true (default) |
| **Lifetime** | `batch.close_graminize_egress` deletes that rule by name as soon as `gsc build`/`sign-image` finish, **before** the batch unit starts, and re-checks that it is gone |
| **On failure to close** | the deploy aborts. An SGX workload silently keeping internet access it was only lent for a `docker build` is exactly the posture this platform exists to avoid |

So the workload itself still runs under `DenyAllOutbound`, same as before.

`TF_VAR_allow_setup_egress=true` remains available but is a blunter instrument:
it rewrites `AllowHTTPSEgress` in place and the rule lives as long as the VM.
Prefer the ephemeral rule above.

> **The pre-built Gramine image comes from the bake.** It is produced by
> `setup_sgx.sh`, so this only holds for images baked with a current CLI. If a
> deploy-time graminize starts compiling Gramine from source, the image predates
> the pre-build — re-run
> `tee-crafter internal bake-ami --tee-platform sgx-azure`.

### First measured MRENCLAVE

Real `Standard_DC2s_v3` hardware, `fintech_fraud_detection`
(`python:3.12-slim`, i.e. Debian 13) graminized by GSC `0b2ba93` with Gramine
1.9:

```
mr_signer: 2002c3a3158dbb05474405a2cd9de8e9def1aa048af238aa22f93211ed26b1ae
mr_enclave: 1fe84b9fb6190fc432b1fe8e0233c6fe51abf235a402f47944504aedcd82a21a
isv_prod_id: 0
isv_svn: 0
debug_enclave: False
```

`debug_enclave: False` matters: the client rejects debug enclaves outright
(§"Client Verification Steps", step 1), so a debug-signed image would have been
refused at connect time.

Reading that value needed a fix of its own. `read_mrenclave_on_vm` overrides the
graminized image's entrypoint with `/bin/sh` — it has to, since the real
entrypoint launches the enclave — and `gramine-sgx-sigstruct-view` is
`#!/usr/bin/python3` importing `graminelibos`, which GSC installs under its own
meson prefix rather than onto the system path. Every invocation therefore died
with `ModuleNotFoundError: No module named 'graminelibos'`, and because the
probe redirects stderr to `/dev/null` the caller saw only an empty string and
recorded `unreported`. The probe now exports `PYTHONPATH` from
`/gramine/meson_build_output/lib/python3*/site-packages` first.

## Attestation Details (batch)

### RA-TLS Certificate

The SGX enclave generates a self-signed TLS certificate at startup that embeds a DCAP quote in an X.509 extension (OID `1.2.840.113741.1.13.1`). The quote's `report_data` field contains `SHA-256(ECDH_public_key)`, binding the enclave's identity to its encryption key.

### DCAP Quote Structure (v3)

```
Quote Header (48 bytes):
 0-1: version (uint16 LE)
 2-3: att_key_type (uint16 LE, 2 = ECDSA-P256)
 4-7: tee_type (uint32 LE, 0x00 = SGX)
 8-47: QE SVN, PCE SVN, vendor ID, user data

Report Body (384 bytes, sgx_report_body_t at offset 48):
 64-95: MRENCLAVE (32 bytes)
 128-159: MRSIGNER (32 bytes)
 256-257: ISV_PROD_ID (uint16 LE)
 258-259: ISV_SVN (uint16 LE)
 320-383: REPORT_DATA (64 bytes) — SHA256(ECDH_PUB) in first 32 bytes

Signature Data (starting at offset 432):
 sig_data_len, ECDSA signature, attestation key, QE report, QE report sig,
 QE auth data, PCK certificate chain (PEM)
```

### Client Verification Steps

1. **Debug Enclave Rejection** — Reject if `ATTRIBUTES.FLAGS.DEBUG` is set (production requires debug-disabled enclaves)
2. **ECDSA Signature** — Verify `ECDSA-P256(SHA256(header + report_body))` with the attestation public key
3. **MRENCLAVE** — Match against the expected value captured from the signed SIGSTRUCT. When the build host had no Gramine and MRENCLAVE/MRSIGNER are `unknown`, the client **exits 1** rather than trusting whatever answers on the port; set `TEE_CRAFTER_ALLOW_UNPINNED_MEASUREMENT=1` to accept trust-on-first-use (it prints a full-width warning banner and is not for production). See `templates/sgx/client.template.py`, lines 360–383.
4. **MRSIGNER** — Match against the expected signing key hash, under the same unpinned gate as MRENCLAVE.
5. **QE Report Binding** — `QE_report_data[:32] == SHA256(att_key || qe_auth_data)`
6. **PCK Certificate Chain** — Verify the chain from the PCK cert to the pinned **Intel SGX Root CA** (`certs/intel-sgx-dcap-root.pem`), including a subject-CN check on the anchor so the wrong certificate cannot be injected at build time.
7. **Public Key Binding** — `report_data[:32] == SHA256(enclave_ECDH_public_key)`
8. **Platform TCB status** — evaluate the platform's Intel TCB level against
 signature-verified collateral, and check every certificate in the PCK chain
 against Intel's CRLs. `OutOfDate` and `Revoked` are fatal.

### What this client does *not* check

Be explicit about the gaps rather than reading them out of the list above.

- **No ISV_SVN floor.** A client could refuse an enclave below a minimum
 `ISV_SVN` and does not. It could not simply be wired up either: the Gramine
 manifest sets no `sgx.isvsvn`, so Gramine signs at 0 and any floor above 0
 would reject TEE-Crafter's own enclaves. What *is* enforced is MRENCLAVE,
 which pins the exact enclave rather than a claimed revision.
- **No client-nonce anti-replay.** RA-TLS binds `report_data` to the enclave's
 ECDH public key (channel binding). The `ratls_nonce` the client generates is
 round-tripped into the audit line only; it is never sent to the enclave and
 never compared.
- **`/input` and `/output` are not verified by the enclave** on a batch run —
 see *The batch I/O paths* above for what covers them instead.

Platform TCB status is **not** in this list: `enforce_platform_tcb_status`
(`templates/sgx/client.template.py:846`) evaluates it through the shared
`tee_crafter_tcb_eval` module, against collateral whose signatures are verified
to the pinned Intel root, and it checks **every** certificate in the PCK chain
against Intel's CRLs rather than just the leaf — revoking a PCK intermediate is
how Intel withdraws trust in a whole class of platform. `OutOfDate` and
`Revoked` are fatal under every policy setting.

## Security Model

| Property | Implementation |
|----------|---------------|
| **Hardware Isolation** | SGX EPC memory is encrypted by the CPU; not accessible to OS, hypervisor, or other processes |
| **RA-TLS Attestation** | DCAP quote embedded in TLS 1.3 certificate. Client verifies ECDSA signature, MRENCLAVE, MRSIGNER, PCK chain, and public key binding |
| **ECIES Encryption** | Ephemeral ECDH-P256 + HKDF-SHA256 → AES-256-GCM with AAD (`b"tee-crafter-sgx-v1-req"` / `b"tee-crafter-sgx-v1-resp"`). Only the enclave (holding the private key in EPC) can decrypt |
| **Length-Prefixed Framing** | 4-byte big-endian length prefix on all TLS messages to avoid `socket.SHUT_WR` issues in Gramine |
| **Network Isolation** | No public IP. SSH only from Azure Bastion subnet. Outbound: HTTPS (conditional), DenyAll catch-all |
| **Least Privilege** | Enclave runs as `tee_enclave` system user. Gramine manifest restricts filesystem to trusted files only |
| **No SSH from Internet** | All access via Azure Bastion with tunneling. NSG denies all inbound except Bastion subnet → port 22 |

## Azure VM Requirements

SGX requires Azure **DCsv3** or **DCdsv3** series VMs, which expose `/dev/sgx_enclave` and `/dev/sgx_provision`. These are only available in select Azure regions. The NSG, setup script, and Terraform template are all tailored for Ubuntu 22.04 on these VM families.

## Security Checklist

- [x] **Debug enclave rejection**: Client rejects connections from enclaves with `ATTRIBUTES.FLAGS.DEBUG` set; production requires debug-disabled enclaves.
- [x] **Hardware attestation**: DCAP quote embedded in RA-TLS cert; client verifies ECDSA-P256 signature over quote header+body.
- [x] **Identity pinning**: Client enforces MRENCLAVE and MRSIGNER from the signed SIGSTRUCT before sending data. If the build host had no Gramine and both are `unknown`, the client **exits 1** rather than falling back to trust-on-first-use; `TEE_CRAFTER_ALLOW_UNPINNED_MEASUREMENT=1` opts back into TOFU behind a warning banner (dev only).
- [x] **PCK certificate chain**: Quote’s PCK certificate is validated up to the Intel SGX Root CA using DCAP/`az-dcap-client`.
- [x] **Public key binding**: `REPORT_DATA` must contain `SHA256(enclave_ECDH_public_key)`; client checks this binding before using the key.
- [x] **Network isolation**: No public IP; all access via Azure Bastion tunnel. NSG denies all inbound except Bastion → SSH, with restrictive outbound rules.
- [x] **Least-privilege runtime**: Enclave process runs under a dedicated `tee_enclave` user; Gramine manifest constrains filesystem and environment to declared trusted paths.
- [x] **Offline dependencies**: Python wheels are downloaded on the deployer and installed from a local cache on the VM to avoid in-enclave package installation from the internet.
- [x] **Log hygiene**: Server-side templates avoid leaking data payloads, keys, or stack traces; client logs focus on attestation state and high-level errors only.
- [x] **TLS 1.3 minimum**: All RA-TLS connections enforce `ssl.TLSVersion.TLSv1_3` as minimum version.
- [x] **AES-GCM AAD**: Request and response payloads use distinct Authenticated Associated Data tags (`b"tee-crafter-sgx-v1-req"` / `b"tee-crafter-sgx-v1-resp"`).
- [x] **ECDH key + RA-TLS certificate rotation**: Server regenerates the ECDH keypair and re-creates the RA-TLS certificate (with fresh DCAP quote) every 3600 seconds.
- [x] **Docker container hardening** (container mode): `--cap-drop ALL`, `--read-only`, `--pids-limit 512`, custom seccomp profile, AppArmor MAC profile.
- [x] **Systemd sandboxing**: `ProtectKernelTunables`, `ProtectKernelLogs`, `ProtectClock`, `RestrictNamespaces`, `LockPersonality`, `SystemCallArchitectures=native`.
- [x] **Ed25519 provenance signing**: Build audit trail cryptographically signed at build time.
- [x] **Sysctl persistence**: OS-level hardening persisted to `/etc/sysctl.d/99-tee-crafter.conf`.
